# C++20 重构实施阶段与验证

主方案暂定 cpp-httplib，Drogon 作为备选。交付顺序为独立常驻后端优先，各类前端通过统一 HTTP API 接入。先围绕 cpp-httplib 验证少量端到端搜索与下载场景，再迁移平台适配、任务和元数据；当前阶段只整理文档，以下实施步骤尚未执行。

实施依据为[后端服务详细设计](backend-service/README.md)，其中模块、目录、模型、路由和状态机是当前目标契约。下面七阶段用于组织验证；详细设计中的 S0～S5 用于描述可交付功能，两者不表示已经执行。

构建固定采用 C++20 + CMake + FetchContent，Git 依赖浅克隆；发布 tag 与期望 commit、工具链和选项统一记录，按[构建与依赖](backend-service/build-and-dependencies.md)执行。仍然先完成设计，本轮不创建构建脚本。

## 阶段一 明确平台范围与候选清单

整理首批平台及其歌曲、歌单、专辑、分类、榜单、音频解析、歌词和封面能力。每项标注对应 Go 方法、凭证要求和协议算法，避免一次承诺迁移所有平台。

完成条件：有首批迁移清单、平台加密需求表，以及可用于离线解析测试的去凭证响应样本。新增网络库先记录到[技术栈选型](technology-stack.md)，再决定是否进入验证。

## 阶段二 验证网络与 TLS

先以 cpp-httplib Server 与 Client 实现最小样例，验证有界线程池、多个前端搜索和持续下载能否满足预期。只保留必要功能，记录编译器与 Release 配置；出现具体能力缺口，或压测调优后仍不满足目标时，再验证 Drogon 备选。

| 场景 | 检查内容 |
| --- | --- |
| 本地服务 | 健康接口、JSON 请求与响应、并发处理、正常退出 |
| 独立运行 | 无界面启动，普通 HTTP 客户端可调用，不依赖 Electron、Tauri 或 Qt |
| 控制与媒体隔离 | 同进程独立监听／线程池，媒体满载、慢消费者下控制 API 不使用媒体线程 |
| 上游请求 | HTTPS GET 与 POST、自定义 UA、Referer、Cookie、超时 |
| 证书校验 | 证书链和主机名正常通过，错误证书与错误主机名连接失败 |
| 重定向 | 跟随策略、次数上限、新连接校验、敏感请求头处理 |
| 文件传输 | 大文件逐块写盘、进度、取消、网络断开、稳定内存使用 |
| 续传 | 正确的 206、Range 被忽略返回 200、416、资源身份改变 |
| 背压 | 写盘或下游变慢时限制缓冲，不随文件大小无限增长 |
| 混合运行时 | 若使用 curl 或 cofetch，验证调度、线程归属、生命周期和退出 |

TLS 先验证 cpp-httplib 支持的后端与所需证书配置；若 Schannel 为硬性条件，单独验证出站 curl。Drogon 的 OpenSSL 或 Botan 路线随备选启用需要再验证。引入独立客户端不自动改变 cpp-httplib Server 主方案。

记录最终可分发文件总大小，包括 DLL、证书包及必要资源，而不是只统计主 EXE。并发传输记录内存和线程数量；不预设某个库一定更小或更快。

完成条件：验证 cpp-httplib 主方案下的 Client、下载传输与 TLS 组合，明确实际并发容量和未覆盖功能。普通排队先通过超时与限流调整，不仅因“阻塞 I/O”标签切换框架。

## 阶段三 建立公共模型与首个平台

建立模型、错误、分页、来源能力、HTTP 传输适配和平台注册机制。先完成一个平台的歌曲搜索、详情、音频地址解析和原始文件下载，让公共契约经过真实调用。

签名与加密使用 Go 实现产生的固定测试向量对照，核对编码、填充和字节顺序。平台解析主要使用离线样本，在线请求用于检查当前可用性，不把网络波动当作解析算法回归。

完成条件：通过 HTTP API 执行搜索并下载正确格式的文件；超时、错误凭证、无结果与接口失败可以区分；平台代码不依赖服务控制器类型。

## 阶段四 迁移集合与发现能力

按优先级加入歌单搜索与详情、专辑搜索与详情、分类目录与分类歌单、榜单目录与榜单曲目。逐项验证远端分页和能力声明。

加入第二个平台后验证多平台搜索的部分成功、来源错误明细和分页信息。分类、榜单的静态目录或搜索包装行为与实时接口分开记录。

完成条件：首批平台的能力矩阵与真实行为一致，未支持能力返回明确错误；单来源故障不导致其他来源的有效结果丢失。

## 阶段五 实现任务下载与换源

将单次下载扩展为服务端任务，提供排队、HTTP 状态／进度查询、SSE 主动推送、取消、重试和批量创建。查询接口独立保留，不要求客户端必须订阅；验证 SSE 线程隔离、身份隔离、慢客户端和重连同步。任务提交前持久化，客户端用 Idempotency-Key 应对提交结果不确定；失败重试创建新任务并关联旧任务。加入检查点与发布协调后再提供进程重启恢复；先完成顺序流式下载，再按收益决定是否增加并发分段。

换源复用公共搜索和探测服务，加入版本、时长和最低置信度规则。通过同名曲、翻唱、Live、Remix、资源失效及试听样本验证误匹配行为。

完成条件：关闭全部前端后，只要后端进程仍运行，已创建任务继续执行；重新连接能查询任务与结果；远程客户端可以通过接口获取有权限的已完成文件；取消能够停止实际传输；续传不会损坏文件；无法找到可靠版本时不返回低分替代。

## 阶段六 验证元数据与轻量依赖

优先验证 TagLib 或有限格式实现对 MP3、FLAC、M4A 的标题、艺术家、专辑、封面和歌词写入。记录只写标签时的音频数据一致性、重复写入行为、未知标签保留、错误恢复和临时文件需求。

容器类格式不能简单比较整文件哈希判断音频是否变化，应提取或定位音频载荷进行比较，并检查目标播放器可读性。若验证环境需要解码检查，可将相关工具作为测试环境依赖，不因此默认打包进产品。

完成条件：支持范围明确，文件可重复读取和播放；不支持的格式按选项保留原始音频、生成独立歌词与封面，或调用可选 FFmpeg。标签能力、属性探测、转码和播放分别记录覆盖情况。

## 阶段七 补齐界面与发布

先发布无界面的独立服务程序，再按使用方式增加新页面、原页面兼容层、CLI 或桌面外壳。各前端使用同一套 API，并能配置本地或远程服务地址。补齐下载历史、本地文件和集合等扩展，并形成固定版本、功能开关及 TLS 后端的发布配置。

完成条件：目标 Windows 环境可以从干净的发布目录启动，依赖文件完整，退出不留下活动请求或损坏记录。若支持其他系统，分别验证构建与运行，不能由 Windows 结果推断跨平台完成。

NAS／Docker 部署另验证 Linux 与目标 CPU 架构、端口、下载目录权限、配置和数据持久化；提供对应部署的启动与重启管理方式。服务接口可以复用，不代表所有部署产物已同时完成。

## 验证重点

| 测试层 | 主要对象 |
| --- | --- |
| 单元测试 | 签名与加密向量、响应解析、版本匹配、去重、文件名和格式识别 |
| 本地集成测试 | 模拟平台、超时与取消、Cookie、重定向、Range、断开与恢复、慢消费者 |
| 文件测试 | 各格式标签、封面与歌词、重复写入、失败回退、音频载荷保真 |
| 在线验证 | 实际平台接口、当前凭证与音质能力，按需要显式执行 |

首轮优先覆盖会造成文件损坏、误匹配或无限资源消耗的路径。接口结构和功能仍在变化时，不为每一层简单转发编写重复测试。

## 待决定事项

- cpp-httplib Client 是否覆盖出站 TLS 和下载需求；必要时采用何种独立客户端。Server 暂定 cpp-httplib，Drogon 为备选。
- Schannel 是否为发布硬性条件，以及是否接受 OpenSSL 或 Botan。
- 首批平台、登录与签名器支持范围。
- 首批音频格式、元数据覆盖，以及可选 FFmpeg 的处理方式。
- 后端服务首版完成后，首个前端的类型与旧页面兼容范围。
- 静态或动态链接、FetchContent 固定版本清单与非标准上游构建适配、目标平台清单。

配套决定逐项写回对应设计文档；其他库保留为研究参考，主方案调整需要具体的验证结果作为依据。
